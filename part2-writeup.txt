Part 2 bits per character

The fixed Transformer is trained on byte-level BPE token ids from the Part-1 cleaned text. part2.py trains that BPE at the requested vocabulary size, writes train.bin and dev.bin, trains the provided model, and writes config.json plus the tokenizer files. Nothing here was run: the training step needs a GPU.

Baseline (V = 50,000), then the official dev number from the fixed evaluator:

    uv run python part2.py --input artifacts/part1/cleaned --output artifacts/part2/ --vocab-size 50000
    uv run python part2_eval_bpc.py --config artifacts/part2/config.json --model artifacts/part2/model.pt --ids artifacts/part2/dev.bin --text artifacts/part2/dev.txt

Baseline dev bpc: fill in from that evaluator. The trainer also prints "final dev bpc" and stores it in artifacts/part2/dev_metrics.json. Report the evaluator's number.

The tokenizer is the same byte-level BPE as Part 1. Merges do not cross newlines, so a newline is token 10. encode then decode reproduces the cleaned text, including blank lines and characters that were rare in training. That is the standard-solution family, so this baseline is the reference the test score is compared against.

Sweep at least four vocabulary sizes with the same tokenizer and the same cleaned text:

    uv run python part2_analysis/sweep.py --input artifacts/part1/cleaned --output artifacts/part2/sweep/ --vocab-sizes 5000,10000,20000,50000

The script skips a size that already has dev_metrics.json, writes bpc_vs_v.tsv and bpc_vs_v.svg, and prints the vocabulary size with the lowest dev bpc. Submit that run (its model.pt, config.json, and tokenizer/) as the optimized system. The sizes match the Part-1 compression sweep.

Bits per character factors as (bits per token) times (tokens per character). Part 1 measured the second factor directly: for every language, tokens per character fell as V went from 5,000 to 50,000, quickly at first and then more slowly. A larger vocabulary is a better compressor. It is not automatically a better language-model tokenization. Each new token type is rarer, so the fixed model has fewer observations per type and a larger embedding matrix, and bits per token tend to rise. The product can therefore bottom out at a vocabulary size where compression is still improving. The sweep separates the two factors (nll per token, and tokens scored divided by characters) so the plot shows which one moves the product. Better Part-1 compression does not always mean lower bits per character; it does when the drop in tokens per character outweighs the rise in bits per token.
